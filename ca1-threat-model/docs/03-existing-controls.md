# Critical appraisal of existing controls
For each: what it is, what it protects, and its LIMITS in THIS context (not generic).

| Control | Present? | What it defends | Limitations here | Evidence |
|---|---|---|---|---|
| NSG firewall (SSH only)  |Yes | Denies all inbound traffic by default, only port 22 from my IP address reach the VM | It protects only the SSH port and has no view of what happens inside the VM or the app. | ssh_my_ip.png |
| SSH key-only login | Yes | Password authentication is disabled, so password guessing and brute force against the VM account fail. | The .pem file is a single factor: if it's stolen or leaked (for example committed to GitHub), the attacker has full  access, no MFA | vm_juiceshop_key.png AND sshkeyonly_evidence.png |
| Localhost-only container + SSH tunnel | Yes | The container is bound to 127.0.0.1:3000, so the vulnerable app isn't reachable from the internet | Traffic between the browser and the app on the VM is still plain HTTP. Anyone with SSH access can open the same tunnel | dockerjuiceshp_runnning(localhost).png |
| Docker container isolation | Yes (default settings) | Runs the app as a non-root user (UID 65532), not privileged, separated from the host's processes and filesystem. | Not hardened: writable filesystem, no memory or CPU limits, default capabilities kept, and no-new-privileges not set. The container shares the host kernel, so a kernel or runtime flaw could allow escape. | docker_inspect.png |
| HTTPS/TLS | No | Nothing | Logins, passwords and JWTs are readable by anyone on the path. Inside the VM it's loopback, and my own route is protected by SSH, but the app itself has no TLS at all. | http_evidence.png |
| WAF / reverse proxy | No | Nothing. A WAF would filter malicious requests (for example SQL injection and XSS payloads), and a reverse proxy could add TLS, rate limiting and hide the app's details. | Every request reaches Juice Shop as-is. Nothing filters injection payloads (threats 11, 12, 15, 84), nothing adds HTTPS (42, 83), nothing limits request rates (16), and there is no central access log. The app's own validation is the only line of defence. | `docker ps` shows one container; `ss -tlnp` shows only sshd (22), the app (127.0.0.1:3000) and the system DNS resolver, so no web server or proxy is listening (screenshots). | 
| Logging & monitoring | Minimal | The Azure Activity Log records management actions (such as my NSG changes). Docker keeps container output logs. | The container logs show only startup and configuration messages; no one monitors them and there are no alerts, NSG flow logs, Azure Monitor agent or SIEM. An attack on the app would probably go unnoticed (to be confirmed during testing). | docker_logs.png |
